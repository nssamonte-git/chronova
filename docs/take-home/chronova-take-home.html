Chronova: a timeline / Gantt scheduler in Jetpack Compose
A short writeup: what was built against each requirement, how the app is designed, how to run it, and how AI was used, checked and steered.

Recorded on a real phone: the voice orb sits above Add task.

Overview

Chronova shows tasks as bars on a horizontally scrollable time axis. You can scroll through time, drag a bar to move it, drag its edges to resize it, and every edit snaps to a configurable grid. The timeline is custom Compose (layout, drawing and gestures written by hand), with no third-party chart or Gantt library.

Running the project
Setup

Running the project: from GitHub to an APK

Everything the Android build needs is in the repository. Nothing to configure: the app connects to the live server and has a demo account. The only extra steps are the ones in the boxes below.

Android Studio

Recent enough for AGP 9.5; brings its own JDK. Install Android SDK 37 when asked.

The code

Git, or a browser for the ZIP. On Windows, install Git for Windows: every build runs a shell script through its bash.

A device

A phone (Android 8.0+) with USB debugging on, or an emulator.

Java, internet

Gradle runs on JDK 25 and downloads it on the first build, with the dependencies: internet needed. Terminal only: any JDK 17+ and ANDROID_HOME.

1

Get the code

Clone it, or on GitHub choose Code → Download ZIP and unzip it.

git clone https://github.com/nssamonte-git/chronova.git
2

Open the Android project, not the repository root

In Android Studio: File → Open → chronova/Chronova - Android App. The first Gradle sync downloads the dependencies (a few minutes). Android Studio finds the SDK and writes it to local.properties by itself.

3

Run it on a phone or emulator

Pick the device in the toolbar and press Run ▶ on the app configuration.

4

Build the APK

In Android Studio: Build → Generate App Bundles or APKs → Generate APKs. Or from a terminal:

cd "chronova/Chronova - Android App" ./gradlew :app:assembleDebug # Windows: gradlew.bat :app:assembleDebug # → app/build/outputs/apk/debug/app-debug.apk
5

Install the APK

With the phone plugged in, or copy the file to the phone and open it (allow installs from that source when asked):

adb install -r app/build/outputs/apk/debug/app-debug.apk
6

Sign in with Try demo

The app opens on the sign-in page. Try demo signs into a shared demo account and loads Sample Project (1,000 tasks). The app uses the live server by default; chronova.apiUrl in local.properties points it at another one (page 15).

Tests, and if something goes wrong

./gradlew test runs the unit tests; ../tools/check.sh runs everything (tests, lint, architecture checks, screenshots, security gate; on Windows, in Git Bash or WSL). A build or install that fails, a phone that isn't found, or a sign-in error: page 3 lists the usual causes and fixes.

How the timeline works
Custom Compose

How the timeline works

Correctness lives in plain Kotlin (:core:timeline), which has no Android code and is unit-tested. The Compose layer only turns time into pixels and finger movement back into time.

Coordinates

One time origin

Times are epoch milliseconds. Every x comes from TimelineMath: x = (t − project start) minutes × px per minute. Pixel → time rounds to whole minutes, because a float at large x can't hold milliseconds. Zoom and scale only change px per minute.

Scrolling

One scroll position

TimelineViewportState is the only horizontal position. Header and grid read it while drawing; bars read it in the layout phase, so scrolling doesn't recompose rows. Nothing is measured at full content width, since a long project at high zoom is wider than Compose can measure. Rows are a LazyColumn.

Gestures

Decide once, recompute from the start

One pointerInput per bar, keyed on the task id. The drag type is fixed at pointer-down. Every move recomputes the bar from the task as it was at gesture start plus the total distance, so rounding never builds up and slow drags don't stick. The preview stays until the saved task arrives (no one-frame flash).

Snapping

The dragged edge snaps

Sub-day steps snap from local midnight; whole days follow real midnights. The 15-minute minimum and the project end are rounded inward, so a clamped edge still lands on the grid. Pinch-to-zoom takes every move until all fingers lift, so it never reaches a bar.

Interaction choices

  • Direct drag. Dragging a bar moves it at once; dragging empty space scrolls. No long-press needed.
  • Resize handles only on the selected bar. Tap to select, then drag an edge. It costs one tap but prevents accidental resizes on small bars.
  • Drags move only their own task. If a drag leaves later tasks overlapping their dependency, a message offers Push, with Undo.
  • Every task always has a row. When its bar is off-screen, an arrow points to it and scrolls it into view.

Beyond the brief
Beyond the brief · 1 of 2

Everything Chronova does beyond the take-home

Planning on the timeline

Four scales

Hours, Days, Weeks and Months. Ticks follow the real calendar (month lengths, daylight-saving days), and whole-day snapping follows local midnights.

Pinch-to-zoom

Two fingers zoom around the point between them. The zoom is saved once when the fingers lift, and it never moves a bar.

Projects

Create, rename and delete projects with a date range of up to 366 days; a range can't shrink past existing tasks. Each project remembers its own view settings.

Duplicate and "Start from"

Any project can be a template: its tasks and links are copied to a new start date, keeping lengths and each task's time of day. The copy starts with nothing done.

Task editor and Undo

Add or edit a task's title, colour, and start and end date and time, or delete it. Drags, edits and deletes can all be undone.

Progress, notes, milestones

Percent complete in steps of 10, shaded on the bar; free-text notes up to 2,000 characters; milestones drawn as diamonds that can be dragged and linked.

Dependencies and Push

Finish-to-start links (cycles are blocked), drawn as arrows that turn red when broken. After an edit, Push moves waiting tasks later just enough, with Undo.

Critical path

A switch outlines in red the tasks where any delay moves the finish, and fades the rest. The editor shows how long a task can slip, in working hours (09:00–17:00, Mon–Fri).

Search, filters and today

Search titles and filter by colour and by not done, done or milestone, with a match count. A line marks now, and one button jumps to today.

AI features

Voice assistant

Tap the orb and speak, e.g. "push Build by two hours and everything after it". It says what will change and applies it only on a spoken yes, with Undo, and offers a clash-free alternative when a change would overlap. It also drives the app: "go to Friday", "switch to weeks", "dark mode", "export this as a PDF".

Schedules from images

Photograph or pick an image of a schedule or Gantt chart to start a project or add to one. Meta reads the image, then OpenAI builds the tasks from what was read (never the image). A preview shows the tasks, milestones and links, with rows to untick, before Apply; Undo afterwards.

Data, sharing, polish and the platform

Data, sync and accounts

Offline first

Projects, tasks and links live in a local Room database (with migrations) and everything works with no connection. Changes are marked unsynced until the next sync.

Sync only when you agree

Sync never runs by itself: coming back online with unsynced changes asks "sync now?". The newest edit per record wins, and a failed sync can simply be run again.

Accounts

Sign up with an emailed 6-digit code, sign in, reset a password. "Remember me" keeps the session with a token encrypted by an Android Keystore key, so later launches work offline.

Staying informed and sharing

Task reminders

Off, when a task starts, or 15 minutes, 1 hour or 1 day before, for every unfinished task in every project. Pushed by the server and backed by the phone's own alarm; shown once either way.

Notifications

A bell opens a page of what happened: syncs, the assistant's changes (with Undo), sign-ins on other devices. Push messages report changes made elsewhere but never sync on their own.

Export

A PDF Gantt chart, a CSV spreadsheet or a calendar (.ics) file, optionally with notes, handed to Android's share sheet. Nothing is sent until you pick where.

Look, feel and polish

Dark theme

System, Light or Dark, chosen on the account page. Both themes take their colours from the logo, so task colours and bar labels stay readable.

Built to hold up

Every screen has screenshot tests in light, dark and 1.5× text. Rotation keeps open sheets, drags and the assistant's state, stress-tested on a real phone.

Branding and the 3D orb

Launcher icons and the launch screen are generated from the logo. The assistant is a 3D orb drawn live with Filament, falling back to a mic icon if 3D isn't available.

The platform behind the app

Laravel server

Laravel 13 on PostgreSQL: sign-up and sign-in with tokens, the sync API, and voice and image endpoints that keep AI provider keys on the server and store no audio or words.

Staff admin panel

A Filament panel; staff need authenticator 2FA by default (an admin can lift or restore it, audited): user management, a health and usage dashboard, an append-only audit log, and time-limited, audited, read-only support access.

AWS

Live on one EC2 instance (Docker Compose, Caddy HTTPS, Secrets Manager). A production stack with CloudFront, Fargate, RDS and SES is written in CDK and tested, not deployed (page 13).

The voice assistant and image import need an account and a connection; the full details are in the repository's README.md, docs/voice-api.md, docs/import-api.md and docs/push.md.

App architecture
Design architecture

MVVM inside a clean three-layer design

Dependencies point inward: presentation → domain ← data. The domain layer is plain Kotlin and knows nothing about Compose, Room or the network.

One drag, end to end

  1. View. TaskLane holds the drag preview (transient UI state). detectTaskGestures and TaskEdits compute the snapped time span on every move.
  2. ViewModel. On release the screen sends the intent commitEdit(original, edited), where original is the task at drag start.
  3. Domain. A use case calls ApplyScheduleChanges: one Room transaction that refuses the change if the task changed since the drag started, and returns the inverse for Undo.
  4. Back up. Room's flow emits, the ViewModel maps it to TaskUi, the StateFlow updates, and the screen redraws.

Wiring is manual dependency injection: AppContainer holds shared pieces, and each feature has a small graph in :app (TimelineGraph, ProjectsGraph, …). No DI framework, so no extra dependency, and tests build their own graphs.

Modularization
Gradle modules

Modules make the layers a compile-time rule

36 modules: the :app shell, 9 core modules, and each feature split into domain / data / presentation (a layer module exists only where that layer has code).

How the rules are enforced

  • verifyModuleGraph fails the build on a forbidden edge (feature → feature, core → feature, domain → data or presentation).
  • Domain modules use the plain Kotlin JVM plugin, so an Android or Compose import there simply doesn't compile.
  • verifyUiModels fails if a composable or UI-state file imports a domain entity: screens render their own UI models.
  • Convention plugins in build-logic (androidApplication, androidLibrary, androidCompose, androidRoom, androidScreenshots, jvmLibrary, moduleGraph) keep every module's build file short and the same.
  • Cross-feature UI goes through the shell. The timeline hosts the voice assistant only through AssistantSlot in :core:ui, built by the navigation host.

Why: the layering started as a convention. When it was split into modules, an architecture audit found 31 layer violations; after the split there are 0, and the compiler now keeps it that way.

AI voice assistant
Beyond the brief

The voice assistant: from spoken words to a saved change

The server and the AI models only propose. The app checks every proposal against its own data, says what will change, and writes only after a spoken yes.

Safety

The model can return only listed operation types on tasks from the request. Words and task titles go in as data, never as instructions; a test with an instruction hidden in a task title was ignored.

One write path

A spoken yes writes through the same ApplyScheduleChanges as a drag, so voice and touch can't disagree, and Undo works the same way.

Measured (12 Nov 2026)

Local server, real providers: about 6 to 9 s from the end of speech to the spoken proposal, and about $0.007 per confirmed command.

  • Push the reviewed release to main; on the instance, a clean checkout pulls it (fast-forward only).

Accounts
Accounts

Three ways in: sign in, sign up, try the demo

The app needs an account: signed out, it opens on the sign-in page and nothing else is reachable. Each way in ends with the same thing, a token the app keeps and sends with every later request.

The token

An opaque Sanctum token, not a JWT. The server keeps only its SHA-256 hash and looks it up on every request, so signing out, a password reset or a disabled account takes effect at once.

Staying signed in

A token lasts 60 days and moves forward each day the app is used. With "Remember me" off, the session lasts only while the app runs.

Forgot password

The same pattern as sign-up: auth/forgot emails a code, auth/reset sets the new password with it, signs out the other devices and signs in here.

App and server
System

How the app talks to the server

REST-style JSON over HTTPS, under /v1: no GraphQL, no open sockets. Push is the only way back.

The requests

AreaRequests (all under /v1)Token · body
Sign-in pagesauth/register, verify, resend, login, forgot, reset (POST)none · JSON
AccountGET me, POST auth/logout, DELETE accountBearer · JSON
SyncPOST sync: up to 500 changes up, then 500 changed records a page downBearer · JSON, 60 a minute
Push devicesPUT devices (push token, time zone, reminders), DELETE devicesBearer · JSON
Voicevoice/transcribe, interpret, explain, resolve, decision (POST)Bearer · JSON; audio as multipart
Image importPOST import/image (off on the live server)Bearer · image multipart

Encryption, from the app to the server and back

On the wireTLS 1.3 both ways: X25519MLKEM768 key exchange, AES-128-GCM, ECDSA P-256 certificate (from a Mac; a phone may pick X25519 or ChaCha20). Release builds refuse plain HTTP.
The tokenOn the phone: AES-256-GCM with an Android Keystore key. On the server: only its SHA-256 hash.
Other secretsPasswords bcrypt, emailed codes HMAC-SHA256 (both one-way); staff 2FA secrets AES-256-CBC with the app key (in Secrets Manager).
Projects, tasksNot encrypted at rest (PostgreSQL, the phone's database). Caddy passes requests on over plain HTTP inside the same machine.

Not in place: certificate pinning, an HSTS header, database encryption (EC2 disk encryption not checked).

Tools, breakdown, and what the AI got wrong

Which tools, and how I broke the problem down

Claude Code (Claude Opus 5.5) in the Claude desktop app, with access to the project, the Gradle build, adb to a real Android phone, and git. No other AI tools.

  1. Spec first. I wrote a detailed prompt: requirements, architecture, required tests, git and logging rules, and "no big unreviewed code dump". First I asked it to revalidate the plan and split it into small batches.
  2. Revalidation. Before coding, it found a Views template (not Compose), minSdk 24 too low for java.time, and gaps in the spec (range, rounding, minimum duration, when a drag saves).

Assessment, struggles, and where I steered

My assessment of the final solution

Good
  • All time math, snapping and edits are pure Kotlin with unit tests.
  • Header and body share one scroll position, so they can't drift.
  • Edits recompute from gesture start: no rounding drift.
  • One write path with stale checks and Undo.
Compromise
  • Fixed 15-minute minimum duration.
  • Resize handles only on the selected bar (one extra tap).
  • Dependency arrows update when a drag ends, not during it.
  • Scope grew far past one screen; more for a reviewer to read.
With more time
  • Auto-scroll when dragging near the edge.
  • Toolbar that fits a 360 dp phone without side-scrolling.
  • Accessibility actions such as "move 15 minutes later".
  • Live dependency arrows during a drag.

Where the AI struggled most, and why

  • Gesture timing. Touch slop and the one-frame flash were both plausible code that compiled; the defect only exists frame by frame on a screen.
  • Layout and measurement. Bars clamped by a narrower parent, and content too wide for Compose to measure, needed real constraints to show up.
  • Visual results. Empty header labels and off-brand button colours passed every test; only screenshots revealed them.
  • Threading. Main-thread database and network calls pass JVM tests and crash on a phone.

Why: the AI reasons from code and unit tests, but these bugs depend on runtime behaviour: frames, layout constraints, pixels and threads. That's why every batch had to end with a device check against numbers predicted before running it.

Where I overrode the AI or decided myself

  • Process: revalidate first and build in small batches, instead of one large generated pass; never report a check that wasn't run.
  • Gesture model: direct drag on the bar (empty space scrolls) rather than long-press; accepted resize handles only on the selected bar.
  • Scope: skipped the optional polish batch (B8) in favour of documentation; after submission asked for a review against the brief, which found the snap-limit bug.
  • Behaviour: a drag moves only its own task, and later tasks move only through an explicit Push with Undo; sync never starts on its own.
  • Hands-on checks: rotated the phone by hand rather than letting the AI force it over adb; versions pinned and at least two weeks old (this caught two too-new server packages).

Build validator
A security gate on every build

The Android build validator

The problem

AI writes plausible code fast, and many Android security mistakes compile, pass tests and slip through review: an exported component with no permission, proceed() on an SSL error, a trust-all TrustManager, secrets in strings.xml, an unobfuscated release. Pentests come too late.

The purpose

A check that runs on every build, the same on every machine and in CI, and can't be quietly skipped. It stops the build while serious findings are unfixed and says how to fix each one.

How it works

  • No skip switch. A finding goes only when the code is fixed or an exception with a written reason is committed; lowering the threshold is a code change seen in review.
  • Everywhere the same. Part of every Gradle build, so tools/check.sh (pre-push hook and CI) runs it too.

What it did in Chronova

  • Installed 13 Nov 2026 from my knowledge repo (v1.0.0, source recorded in INSTALLED.md). First scan: 0 critical, 0 high, 3 medium, 2 low.
  • Proved it blocks: a planted onReceivedSslError → proceed() failed the build (AND-WV-007, critical), then was removed.
  • Surfaced a decision: release R8 skipped the app's own code. I switched on full R8 (618 of 622 classes renamed); the rule doesn't know AGP 9's optimization setting, so that, and the Keystore-encrypted token store, are reasoned false positives.
  • Today: 521 files, 89 rules, pass; 7 warnings to review before release, 2 suppressed with reasons.

Limits: it is a pattern-based source scan, so heuristic rules can raise false alarms or miss things. It doesn't replace dynamic testing or a pentest, and it is only as good as the threat library behind it.
