# Decisions

Active durable decisions only. Full rationale is in `README.md` ("Decisions and trade-offs") and `docs/AI_USAGE_LOG.md`.

## 2026-11-11: Single scroll authority

- Decision: one horizontal scroll position in `TimelineViewportState` (2026-11-11 revision for multi-project ranges; previously a `horizontalScroll` `ScrollState`). Header and body feed it via `scrollable(reverseDirection = true)`; header, grid and bars read it in draw/layout. Bars are clipped to a page-quantized compose span; rows are a `LazyColumn`.
- Reason: no drift between header and body, no recomposition per scroll frame, and user-defined project ranges can be far wider than a layout can measure.
- Constraint: never measure timeline content at full width; a bar container wider than its lane needs `wrapContentWidth(unbounded = true)` or `width` gets clamped.
- Revised 2026-11-13 (user choices): while a search or filter is on, the list is only the matches and every match gets a row wherever it is in time, and the view scrolls to the earliest; search and filters live in the ViewModel's memory only and end with the screen.
- Revised 2026-11-12 (user choice): rows list only the tasks whose time overlaps what is on screen (`TaskVisibility`), updating as you scroll, plus the selected task (a drag selects its bar, so it never loses its row) and any the assistant just highlighted; with none on screen the timeline says "No tasks here". The list is a `derivedStateOf`, so rows recompose only when it changes, not per scroll frame.
- Revised 2026-11-13 (user choice, replacing the revision above): every task has a row at every zoom (a search's matches while one is on), so the grid pans freely both ways; zoomed in, the on-screen-only rows left little to pan down to and came and went while panning sideways. A row whose bar is off-screen shows an arrow at that edge, in the task's colour; tapping it scrolls the bar into view. `TaskVisibility` is gone; the list is still a virtualized `LazyColumn`, and bars outside the composed span still aren't laid out.

## 2026-11-11: Gesture model

- Decision: dragging a bar moves it directly. Empty space and the header scroll. Resize handles appear only on the selected bar (20 dp outside + up to 20 dp inside each edge; the middle third always moves). Dragging never moves other tasks.
- Reason: a user choice (direct drag over long-press). It also prevents accidental resizes.
- Revised 2026-11-13 (user choices): a drag still moves only its own task. When a drag, a resize or an editor save leaves tasks that wait for it starting before it ends, a snackbar offers "Push": `PushDependents` moves them later, just enough, keeping their lengths (`DependentsRescheduler`, now in `:core:domain` and shared with the assistant), through `ApplyScheduleChanges` with Undo. Moving a task earlier never pulls its dependents along; when pushing would run past the project's end, the snackbar says so and nothing moves.
- Constraint: one detector per bar. The mode is chosen at pointer-down. The preview is local and committed on release.

## 2026-11-11: Time model and snapping

- Decision: epoch-millis timestamps; minute-resolution pixel → time; `floorDiv` nearest snapping from local midnight; fixed 15-minute minimum duration; limits (minimum duration, window end) rounded inward to the snap grid so the dragged edge stays on it. Each project's window runs from local midnight of its start date to the midnight after its end date (up to 366 days, `Project.window(zone)`); the take-home's fixed 3-day window from 2026-03-02 survives only as the first-launch sample project.
- Reason: exact round-trips, symmetric negatives, and a 13:30 task stays valid at 60-minute snap.

## 2026-11-11: Calendar time model

- Decision: four scales (Hours, Days, Weeks, Months). Zoom is the width of one nominal unit (a month is 365.25/12 days), but ticks follow the real calendar (local midnights, Mondays, the 1st). Snap options per scale (Hours 15m/30m/1h, Days 1h/6h/1d, Weeks 1d, Months 1d/1w); whole-day snaps follow local midnights. View settings are stored per project in the local-only `view_settings` table (Room v2, `MIGRATION_1_2`).
- Reason: multi-month projects need longer scales, and day-or-longer grids must survive DST.
- Added 2026-11-12 (user request): pinching the grid zooms too — spreading zooms in, pinching together zooms out — continuously within the scale's limits (`TimelineConfig.zoomedBy`), keeping the time between the fingers in place (`ViewportMath.rescaleAround`), live while pinching and saved once when the fingers lift. Once a second finger lands, every move and lift is consumed until all fingers are up, so a pinch never drags a bar, scrolls or taps.

## 2026-11-11: Task dependencies

- Decision: finish-to-start links only, stored in `dependencies` (Room v3, `MIGRATION_2_3`) with a project foreign key but no task foreign keys (a sync may deliver a link before its tasks). Cycles and self-links are blocked in the editor (`DependencyRules.forbiddenPredecessors`); violations (successor starts before predecessor ends) are drawn red, never auto-fixed by edits (since 2026-11-13 a "Push" is offered after a change; see Gesture model). Deleting a task tombstones its links; undo restores both.
- Reason: the common Gantt case, with no surprising automatic rescheduling. (A voice command can ask to push dependents — see Voice editing.)

## 2026-11-13: Critical path

- Decision (user choices): `CriticalPath` (`:core:domain`) works on the schedule as it is (the scheduled dates, finish-to-start links): the finish is the latest task end; going back from it in reverse link order, a task's latest finish is the earliest latest start of the tasks that wait for it (or the finish), and its slack is that minus its end. Slack 0 or less is critical; a broken link gives negative slack, so it counts as critical. Links in a cycle are ignored. A "Critical path" switch in the timeline settings marks critical bars and diamonds with a red outline (the theme's error colour), fades the others to 45%, draws links between two critical tasks darker and thicker, and puts a red mark in the name cell; bars also say "On the critical path" to TalkBack. The task editor always says, for a saved task, "On the critical path: any delay moves the finish (date)" or "Can slip 3 h 30 min without delaying the finish", and drops the line once its times are changed there. The switch is remembered per project on this device: `TimelineConfig.showCriticalPath`, the local-only `view_settings.critical_path` column (Room v6, `MIGRATION_5_6`, off for existing rows); it is never synced.
- Reason: shows which tasks hold up the finish without a scheduling engine; nothing is moved automatically.
- Revised 2026-11-14 (user choice: a fixed 09:00–17:00, Monday to Friday working day): slack is measured in working time (`WorkingTime`, `:core:domain`), so a night or a weekend between linked tasks is no slack and a chain that is back to back in working time is critical. A task scheduled wholly outside those hours (a Saturday, an evening) is still measured by the clock; a milestone counts as work when it stands in working hours. The editor says "Can slip 6 h of working time…", in hours only (a working "day" is 8 hours). The hours are one constant, not stored or synced; a per-project setting would replace that constant.

## 2026-11-13: Task progress, notes and milestones

- Decision (user choices): a task has `progress` (0–100; 100 is done, set in one tap by "Mark done"), free-text `notes` (at most 2,000 characters, may be empty) and `isMilestone`. A milestone is a moment, not a span: it ends when it starts, lies inside the project (before its last midnight), is either done or not (progress 0 or 100), is drawn as a diamond, and is dragged but never resized (made only by the editor's switch, never by shrinking a bar). `SchedulerTask`'s `init` enforces the shape; `TaskRules` also reports notes that are too long and bad progress. Room v5 (`MIGRATION_4_5`) adds the three columns with defaults (not started, no notes, not a milestone).
- Sync: the three fields are optional on push (sync protocol rule 9): the server keeps the stored `progress` and `notes` when a push leaves them out, so an app from before them can't blank them; a push without `milestone` isn't one (such an app can't make one). Pulls always carry all three; the app defaults any that are missing and skips a pulled task that breaks the rules, and a stored row that breaks them is left out of reads rather than failing them.
- Notes stay private: never sent to the voice providers, never shown in the staff admin panel (which shows titles and dates only).
- Voice (user choice): the assistant can set progress ("mark design done", `set_progress`) and add milestones (`create_milestone`); the interpret context carries each task's `progress` and `milestone` (optional, for older apps), never its notes. A milestone moves like a task but has no length to change, and never counts as overlapping a task (a moment during work isn't a clash); dependency clashes still count.
- Reason: progress and milestones are the basic Gantt features the app lacked; the three changes share one migration and one sync-contract change.

## 2026-11-13: Task reminders

- Decision (user choices): one choice per device (Off / at start / 15 min / 1 h / 1 day before; `ReminderLead`, stored in `chronova_reminders` preferences, not synced, off by default) on the account page, which asks for the notification permission (Android 13+) when one is chosen. Reminders come for every task and milestone not done, in every live project, only while signed in. New module `:feature:reminders:{domain,data}`: `ReminderEngine` keeps exactly one inexact `AlarmManager.setAndAllowWhileIdle` alarm for the next reminder (no exact-alarm permission), posts everything due since it last ran when the alarm fires (never twice; over a day late is dropped), and on any change (tasks, project names, the choice, sign-in; boot, update, time or time-zone change through a receiver) starts afresh from now, so a reminder whose time has passed is never posted late. Notifications use their own "Task reminders" channel and open the task's project. The receivers reach the engine through `ReminderHost` (the Application).
- Reason: reminders without a background library, an exact-alarm permission or a server.
- Revised 2026-11-13 (user choice, `docs/push.md`): the server now pushes reminders too, and the phone's alarm stays as the backup. The device registration carries the reminder choice and time zone; `SendDueReminders` runs every minute on the scheduler and pushes each device's synced tasks that are not done, in live projects, whose reminder came due since the last run (never over a day late; `sent_reminders` stops a second send to a device). The push carries the wording's facts and the phone posts it through the same poster and notification id. A shared "posted" log (`ReminderLog.firstTime`, key `taskId@atMillis`, kept 2 days) means push and alarm post once between them, whichever comes first. The phone's own copy of a task wins: if it is done here or due at another time here (an unsynced change), the push is dropped and the alarm covers it.
- Reason for the revision: a reminder reaches every signed-in device, including one that has not opened the app since the change was synced; the alarm still covers changes not synced yet and works without the server.

## 2026-11-13: Export

- Decision (user choices): a project exports as a PDF Gantt chart, a CSV spreadsheet or an iCalendar file, from "Export…" in its menu; a switch (on by default) puts task notes into the CSV and calendar files (the PDF has none). New module `:feature:export:{domain,data,presentation}`: the CSV (RFC 4180, CRLF, UTF-8 with a BOM, local times) and calendar (RFC 5545: UTC, a UID per task, milestones without DTEND, escaped text, lines folded at 75 octets) builders are pure Kotlin; the PDF is drawn with Android's `PdfDocument` (A4 landscape, the whole date range fitted to the width, always light); the file is written to `cache/exports` (cleared each time) and handed to the share sheet through a FileProvider with a read grant. The projects feature only reports "export this project"; the shell shows the sheet. No new libraries.
- Reason: share or print a plan, take it into a spreadsheet or a calendar, without a server and without sending anything until the user picks where.

## 2026-11-13: Projects as templates

- Decision (user choices): there is no separate template store; any project can be the starting point of another. "Duplicate" (project menu) and "Start from" (new-project sheet) run `CopyProject`: the copy keeps the source's length and starts on the chosen date; tasks move by whole calendar days in the zone (`CalendarDays.shift`), so local times survive DST, and a task DST would make invalid keeps its length instead; progress resets to 0; titles, notes, colours, row order, milestones and links are kept, with new ids. The project, its tasks and links are written in one Room transaction (`createProjectWithSchedule`) and sync like any other new rows.
- Reason: templates without a new kind of stored or synced data.

## 2026-11-13: Schedules from images

- Decision (user choices): a user photographs or picks an image of a schedule or Gantt chart, and it becomes a new project ("Start from: An image of a chart…") or tasks in the open project (the timeline's "Add tasks from an image"), after a preview where rows can be unticked and a chart without dates gets a start date; Undo afterwards (`docs/import-api.md`).
  - The server reads the image with Meta's Model API (Muse Spark reads the text, axis and rows; SAM 3.1 finds the bars) and has OpenAI build the schedule from Meta's results only, never the image. Standard Meta models only (no training on the images); the image is held in memory, never stored.
  - `BarMatcher` turns pixels into columns. Muse Spark's pixel positions drift, so it takes rows and the axis from SAM's boxes when they line up, keeps only boxes with real colour (`BoxColours`, PHP GD, added to the server image), and passes Muse Spark's own reading of each bar beside the measurements for OpenAI to reconcile.
  - `ImportValidator` checks the answer as `ProposalValidator` does for voice. The app plans with `TaskRules` and `DependencyRules` and writes through `createProjectWithSchedule` / `ApplyScheduleChanges`.
  - New module `:feature:chartimport:{domain,data,presentation}` ("import" is a Kotlin keyword). Images are turned upright, scaled to 2048 px and re-encoded without metadata on the phone; the camera and the photo picker need no permission.
  - Off by default on AWS (`-c import=on`); limited to 5 a minute and 50 a day per user.
- Added 2026-11-14 (user choice): a one-day task takes the hours written on the chart ("10–1" → 10:00–13:00, `startTime`/`endTime`); without readable hours it stays a whole day, 00:00 to 24:00, not the 09:00–17:00 working day.
- Reason: the user's request and choices; measured on real charts, the pieces each fix what the other gets wrong (Muse Spark reads text and spans but not exact positions; SAM finds exact boxes but no text and includes the pale tracks).

## 2026-11-13: Push notifications (Firebase Cloud Messaging)

- Decision (user choices): reminders and three alerts ("changes on another device", "new sign-in", "password changed / signed out") reach the phone through FCM HTTP v1, project `chronova-ece3c` (`docs/push.md`). The server sends data messages only and the app words and posts every notification itself (channels, tap actions, the reminder choice and duplicates in one place). Devices register per sign-in (`PUT /v1/devices`: FCM token, time zone, reminder choice) and go with it (sign-out, reset, expiry, account deletion). The server signs Google's OAuth JWT with PHP's openssl (no new server package); the app adds the Firebase BOM 35.1.0 (messaging only, no analytics, no token until a signed-in app asks) and the google-services plugin 4.5.0. `PUSH_SENDER=fake` is the default everywhere, and tests always use it (`phpunit.xml`); `fcm` locally needs `FCM_CREDENTIALS` (the key file, `server/storage/credentials/`, git- and Docker-ignored) and on AWS `-c push=on` with the `PushKey` secret (`FCM_CREDENTIALS_JSON`, web, worker and scheduler only). Notifications show the logo's one-colour hourglass in the status bar and the full-colour app icon beside the text (user request).
- Reason: reminders and account alerts reach every signed-in phone without the app running; wording and duplicate handling stay on the phone; the key never leaves the server.

## 2026-11-11: Offline first, sync on request

- Decision: Room on the phone is the working copy; every write stamps `updatedAt` and marks the row dirty, and deletes are tombstones until synced. Sync never starts on its own: coming back online with unsynced changes shows a prompt, and only "Sync now" (prompt, button, account screen) runs `SyncEngine`. Conflicts: last write wins per record by edit time (server clock as ceiling, ties to the server); a stale push gets the winning copy back. Contract: `docs/sync-protocol.md`.
- Reason: a user choice (asked to be prompted rather than synced silently); per-record last-write-wins is simple and predictable.
- Constraint: once signed in, the app works fully without a connection; blocking Room and network work runs on `Dispatchers.IO`.
- Revised 2026-11-13 (user choice, `docs/push.md`): when a sync changes something, the user's other devices get a "changes on another device" push (at most one per device every 10 minutes). It still never syncs by itself: the phone shows a notification, and tapping it opens the sync prompt ("Changes on another device… Sync now?").
- Revised 2026-11-12 (user request): the app needs an account — signed out, it opens on the sign-in page (`AppGate`) and nothing else is reachable; signing out or deleting the account returns there. A build with no server URL can't sign in, so it stops at that page (user request, same day: sign-in is required even without a server).
- Revised 2026-11-15 (user choice): one exception. "Try demo" on the sign-in page syncs once right after it signs in, so the demo project appears without a tap on Sync now (see "Try demo" below). Every other sync still starts only from Sync now.

## 2026-11-11: Backend — Laravel + Postgres + Filament on ECS Fargate + RDS

- Decision: replace the (never deployed) AWS serverless backend (Cognito, HTTP API, Lambda, DynamoDB; kept at git tag `serverless-backend-v1`) with a Laravel 13 app in `server/`: Postgres, Sanctum tokens, Filament 5 admin, hosted on ECS Fargate + RDS in the user's AWS account. The `/v1/sync` contract (`docs/sync-protocol.md`) is unchanged.
- Reason: the user wants an admin back-office (user management, health dashboard, staff roles + MFA + audit log, audited support data access) and the data is relational; cross-user reporting on DynamoDB would need extra pipelines.
- Trade-off: a database and containers that run all the time (≈ $60–70/month for dev on AWS, see DEPLOY.md) and auth flows that are now ours to secure.
- Revised 2026-11-14 (user request). Staff need 2FA by default. An admin can disable or restore the requirement for another staff member, with both changes audited. The admin panel and server scheduler use Philippine time. Stored timestamps use UTC.

## 2026-11-12: AWS shape

- Decision: CloudFront (default domain, HTTPS) → CloudFront VPC origin → internal ALB → ECS Fargate (ARM64) web + jobs; RDS Postgres in isolated subnets; no NAT gateway (tasks in public subnets, ingress only from the ALB); Secrets Manager for APP_KEY and DB credentials; SES via the task role; ECS Exec only on the jobs service (for `chronova:create-staff`). Voice provider keys live in a `VoiceKeys` secret (created empty, filled by hand) given only to the web container; voice is off unless deployed with `-c voice=on`, and deploying with it off is the kill switch.
- Reason: no domain needed, no way to bypass CloudFront (so `CloudFront-Viewer-Address` is trustworthy for rate limits), lowest fixed cost; provider keys never in code, the template or other containers.
- Revised 2026-11-14 (user choices for the first deploy): the `prod` stage straight away, in ap-southeast-1 (Singapore), starting with an empty database (nothing copied from the local server), Docker images as before. Mail comes from the user's own domain: `-c mailIdentity=domain` verifies the whole domain in SES with Easy DKIM (three CNAME records, printed as stack outputs and added by hand at the domain's DNS host, which is not Route 53) and limits sending to that domain; without it, SES still verifies the single address by email.

## 2026-11-14: Live EC2 deployment

- The deployed environment uses Docker Compose on Sydney EC2, local PostgreSQL, Caddy HTTPS, and Cloudflare DNS. The ECS Fargate and RDS design above describes the separate CDK stack.
- The EC2 role reads `chronova/prod/runtime` in Secrets Manager. The deployment passes credentials to the intended containers through a Compose override. See [the EC2 operations runbook](server/infra/EC2.md).
- Revised 2026-11-15 (user request): the app's build uses the live server, `https://chronova.meenux.tech`, by default (`app/build.gradle.kts`), so a fresh clone builds and connects with no setup; `chronova.apiUrl` in `local.properties` still overrides it. The live domain is now in the repository and the README (it used to be kept out).

## 2026-11-15: Try demo

- Decision (user request and choices): the sign-in page has a "Try demo" button above the form. It signs into the shared demo account `test@chronova.com` (created already confirmed on the live server, with "Sample Project" and 1,000 tasks) and then syncs once. The demo login is a constant in `:feature:account:domain` (`DemoAccount`), committed by the user's choice, although HANDOFF's guardrails keep secrets out of commits: it is a public demo login, not a secret, and anyone could read it from the APK either way. ## 2026-11-12: One apply path for schedule changes

- Decision: drags, the task editor, delete/undo and voice or typed commands all write through `ApplyScheduleChanges`: one Room transaction that applies a list of `ScheduleChange`s only if every record is still exactly what the change was computed from (content compare, not an `updatedAt` version) and returns the inverse list for Undo. A drag commits `commitEdit(original, edited)` with the task as it was at drag start.
- Reason: manual and voice edits share one tested path; edits that arrive meanwhile (another edit or a sync) are never overwritten, with no schema change.

## 2026-11-12: Voice editing

- Decision: the server only proposes. The phone records (the turn ends on silence; at most 60 s), the server transcribes (ElevenLabs Scribe, with the project's task titles as key terms) and interprets (OpenAI, strict JSON schema, re-validated by the server), and the app plans the operations against its current data. The assistant is voice-only (2026-11-12 revision; previously a sheet with a text field and an Apply button): a 3D orb says the change and asks, applies only on a spoken yes (no, silence or tapping away changes nothing; other words are a corrected request), then hides and says what changed while the task is highlighted; Undo follows. Before asking, the app works out the clashes the change would cause (new overlaps, newly broken dependencies); the assistant names them and asks whether to apply it anyway — clashes are allowed, never blocked. Spoken answers are written by OpenAI and said by ElevenLabs in the user's chosen voice (`OYTbf65OHHFELVut7v2H`). "Push everything after it" (dependents) is available only through commands. Voice is on for every signed-in user, bounded by per-user, per-endpoint rate limits, a kill switch and admin usage metrics. Provider keys stay on the server (one server key for everyone, never per-user or on the phone); OpenAI is called with `store: false`; no audio is stored. Revised 2026-11-12 (user choice): each user's requests and answers are kept 90 days in `voice_decisions` and sent back with that user's own requests as history, deleted with the account, never shown to staff (`VOICE_LEARN_DECISIONS` switches it off). Clashes get a clash-free alternative suggested by the model (`/resolve`) and re-checked by the app, which falls back to its own fix (user choice: model suggests, app checks). The interpreter's fixed rules are cached at OpenAI (explicit breakpoint, shared key); user content never is. Fakes are the default for development and tests.
- Revised 2026-11-14 (user request, after odd offers in the walkthrough recording): the app's check of a model's clash-free alternative is stricter (`SensibleAlternative`). It is refused when it moves, adds or deletes a task the plan didn't, other than one that waits (through links) for a task the plan changed, or when it moves a task out of working hours (09:00–17:00, Monday to Friday, the critical path's `WorkingTime`) that the plan left inside them. The model's rules say the same. The app's own fallback (push what waits, just enough) is unchanged and isn't held to working hours, like the timeline's Push.
- Revised 2026-11-13 (user choices): voice also drives the app (see Voice actions). Look-only requests run at once without a yes; writes still need one.
- Reason: user choices (providers as in the brief, always preview then confirm with a spoken explanation, dependents via voice only, on for everyone, task names sent to the transcriber); a model can only propose allowed operations on listed tasks.
- Constraint: real providers only with the user's approval; the privacy policy and Play Data safety form must cover ElevenLabs and OpenAI before release (`docs/voice-api.md`).
- Revised 2026-11-14 (user choice, client handoff): the app's own text describes features only. It names no provider and says nothing about APIs, servers or data handling (the assistant's first-use notice and the image-import note included); provider names, what is sent and the 90-day history belong in the privacy policy and the Play Data safety form, which must exist before release.

- Revised 2026-11-15 (user request): spoken answers use Eleven v4 Turbo (`eleven_v4_turbo`, the latest real-time ElevenLabs model, about Flash v2.5's latency) with audio tags for an energetic, upbeat delivery. The server's `AudioTags` puts `VOICE_ELEVENLABS_STYLE_TAGS` (default `excited, cheerful`) before every spoken line, only for models that act on tags, after taking square brackets out of the words; the explainer is asked for an upbeat tone but writes no tags itself, so every tag sent is a known one; the app's caption stays plain text. Trade-off: about twice Flash's price per character.

## 2026-11-13: Voice actions

- Decision (user choices):
  - The assistant answers with **actions** as well as schedule operations. Actions change nothing, so they run at once without a yes, and the assistant says what it did:
    - going to today, a day or a task;
    - scale, zoom, row height and critical path;
    - search, clearing it, and opening a task's editor;
    - going to another project, the projects, notifications or the account;
    - theme, reminders, sync and export (export opens the share sheet, so nothing is sent until the user picks where).
  - Writes keep the spoken yes: schedule edits, "undo that" (the assistant's own last change, previewed) and new or copied projects (Undo deletes them). Deleting a project stays manual.
  - The orb is on the timeline and the project list. From the list, only actions and new projects make sense; an edit is answered "Open a project first."
  - Revised 2026-11-13 (user request): when the app opens on the project list, the orb greets once per opening. The very first time it gives a short introduction ("Hi, welcome to Chronova! I'm your assistant…"), after that "Welcome back! Tap me whenever you need me." It only speaks: nothing is recorded, and only the fixed words are sent to be voiced; offline or signed out it waits. A project's timeline no longer introduces itself (it would repeat the app's introduction); the record of the introduction (`voice_introduced_projects`) now holds "app".
- How it works:
  - Apps opt in with `capabilities: ["actions"]`; older apps never receive actions or the new operations, so their answers keep their old shape.
  - Requests carry what the screen shows (`context.view`: scale, critical path, selected task, search) and the user's projects, so "this task" and "open Jnn" are understood.
  - Up to 5 actions run in order. Leaving the screen comes last and only once said.
  - Screen actions reach the timeline through `AssistantSlot.viewRequest`. App actions go to the shell as an ordered queue (`AssistantViewModel.appRequest`), which uses the existing ViewModels and use cases.
  - `CopyProject` moved to `:core:domain` so "Duplicate" and the assistant share it.
- Reason: hands-free use of the whole app with no new risk; anything that writes still says what it will do and waits for a yes.
- Constraint: every action is checked like an operation (exact fields, ids from the request, real dates) by the server and again by the app. A new action needs the schema, the validator, the prompt, the fake interpreter, `docs/voice-api.md` and the app's mapping together.

## 2026-11-12: Branding

- Decision: the supplied logo (`docs/brand/chronova-logo.webp`) is used as is, not redrawn: `tools/brand/generate.py` cuts the adaptive, themed and launch-screen icons and the admin logo and favicons from it. The app stays light-themed; the admin panel is dark-only in the logo's colours.
- Revised 2026-11-13 (user choice): the app has a dark theme as well. It was System (following the phone) by default until a later revision the same day made Light the default (user choice; the window colour before the app draws is light for everyone, so the dark night-mode one was removed). ## 2026-11-12: Modular three-layer architecture

- Decision: the Android app is split into Gradle modules: `:app` (shell and manual-DI composition root), `:core:{model,timeline,domain,database,network,data,designsystem,ui,testing}` and `:feature:{projects,timeline,notifications,sync,account,assistant,export,reminders}:{domain,data,presentation}`, with a layer module only where the layer has code (projects and timeline have no data module; they use `:core:data`). `presentation → domain ← data`; features never depend on each other; core never depends on features; `verifyModuleGraph` (build-logic) fails the build on a forbidden edge. Domain modules use the plain Kotlin JVM plugin. ViewModels read through read-only domain query interfaces (`ProjectQueries`, `NotificationQueries`, `AuthQueries`, `SyncStatusQueries`, `SyncPromptQueries`; the repository contracts extend them, so a ViewModel holding one can't write) and change data only through use cases (revised 2026-11-13, user choice: removes the read-only pass-through use cases; reads with logic stay use cases); ViewModels never get a repository, the HTTP client, the recorder or player, or `Context`. Cross-feature UI is wired by the shell (`AssistantSlot` in `:core:ui` for the assistant on the timeline). Build settings live in convention plugins (`build-logic/convention`).
- Reason: a user request (modular, clean three-layer architecture), following the canonical mobile modular clean-architecture standard; the compiler now enforces what was a convention (the audit found 31 layer violations, now 0).
- Constraint: new code goes in the module that owns it; a feature reaching another feature goes through `:app` or a `:core` contract; strings and images live with the module that uses them (shared ones in `:core:ui`/`:core:designsystem`).
- Use cases are wired only in `:app` — `AppContainer` holds the shared pieces and each feature has its own graph in `noel.chronova.app.di` (2026-11-13) — (tests build their own); domain holds no wiring helpers. `verifyModuleGraph` also checks test-only dependencies (tests may additionally use `:core:testing`).
- Decision (revised 2026-11-13, user choice: "everywhere, timeline too"; replaces the 2026-11-12 exception that let screens render domain models): screens and UI state use presentation-owned UI models (`TaskUi`, `ProjectRowUi`, `NotificationUi`, `AccountAuthUi`, `SyncUi`/`SyncPhase`, `ProposalLineUi`, …), mapped from the domain in a ViewModel or a `*UiMappers.kt` per feature.
